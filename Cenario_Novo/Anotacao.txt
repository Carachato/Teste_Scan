/* REXX - Copia listings do ChangeMan para um PDS de destino */
TRACE O

/* 1. Defina aqui as variáveis do seu ambiente */
pkg_id   = "NOME000001"                  /* Número do pacote ChangeMan */
lst_pds  = "SEUPREF.CMNSTAGE."pkg_id".LST" /* Dataset de Staging (LST)  */
dest_pds = "SEUPREF.RELAX.LISTINGS"      /* Seu PDS de destino        */

SAY "Iniciando cópia dos listings do pacote " pkg_id "..."

/* 2. Inicializa o ambiente de serviços de biblioteca do ISPF (LMINIT) */
ADDRESS ISPEXEC "LMINIT DATAID(LSTID) DATASET('"lst_pds"') ENQ(SHR)"
IF RC <> 0 THEN DO
   SAY "Erro ao inicializar o PDS de Staging: " lst_pds
   EXIT 8
END

ADDRESS ISPEXEC "LMINIT DATAID(DESTID) DATASET('"dest_pds"') ENQ(SHR)"
IF RC <> 0 THEN DO
   SAY "Erro ao inicializar o PDS de Destino: " dest_pds
   ADDRESS ISPEXEC "LMFREE DATAID(LSTID)"
   EXIT 8
END

/* 3. Abre a biblioteca de origem para leitura dos membros */
ADDRESS ISPEXEC "LMOPEN DATAID("lst_pds") OPTION(INPUT)"
member = ""

/* 4. Loop para ler cada membro e copiar para o destino */
DO FOREVER
   /* Busca o próximo membro da lista */
   ADDRESS ISPEXEC "LMMLIST DATAID("lst_pds") OPTION(LIST) MEMBER(MEMBER)"
   
   /* Se RC = 8, significa que chegou ao fim dos membros */
   IF RC = 8 THEN LEAVE 
   IF RC > 8 THEN DO
      SAY "Erro ao ler a lista de membros. RC="RC
      LEAVE
   END
   
   /* Copia o membro atual da origem para o destino */
   ADDRESS ISPEXEC "LMCOPY FROMID("lst_pds") FROMMEM("member") TODATAID("dest_pds") TOMEM("member") REPLACE"
   
   IF RC = 0 THEN 
      SAY "Membro " member " copiado com sucesso."
   ELSE 
      SAY "Falha ao copiar membro " member ". RC="RC
END

/* 5. Fecha e libera os datasets alocados */
ADDRESS ISPEXEC "LMCLOSE DATAID("lst_pds")"
ADDRESS ISPEXEC "LMFREE DATAID("lst_pds")"
ADDRESS ISPEXEC "LMFREE DATAID("dest_pds")"

SAY "Processo concluído!"
EXIT 0

Você é um Arquiteto de Software Principal Especialista em Migração de Sistemas Legacy e Modernização de Mainframe para Nuvem. Seu objetivo é absorver e dar continuidade a uma estratégia detalhada de transpilação automatizada de um ecossistema COBOL para Python/AWS Glue (PySpark).

---

### 1. CONTEXTO DO AMBIENTE LEGADO (INPUT)
O sistema possui cerca de 10.000 linhas de código e uma infraestrutura complexa de Mainframe dividida em pastas estruturadas:
- /jcl/: Jobs de controle de fluxo de execução (.jcl).
- /cobol/: Programas principais e subprogramas customizados (.cbl).
- /copybooks/: Layouts de arquivos posicionais textuais (.cpy).
- /dclgen/: Declarações de tabelas relacionais do DB2 (.dcl).
- /cartoes_sort/: Parâmetros inline ou externos de SYSIN do DFSORT/ICESORT (.srt).
- /planos_db2/: Parâmetros de BIND/PLAN e execuções via IKJEFT01 (.pln).
- /load_unload/: Utilitários de carga e descarga de dados (DSNTIAUL).

Particularidades críticas conhecidas do legado:
- IMS (Banco Hierárquico) lidando com transações online e estruturas aninhadas.
- DB2 (Banco Relacional) acionado via cursores linha a linha (FETCH) em rotinas Batch.
- Subprogramas chamados via CALL transitando memória por referência através da Linkage Section.

---

### 2. PREMISSA DA ARQUITETURA ALVO (OUTPUT)
A modernização deve gerar um código Agnóstico (Independente de Ambiente) controlado por uma variável de ambiente (`AMB_EXECUCAO = "LOCAL" ou "AWS"`). O mesmo código deve rodar em:
- Ambiente LOCAL (On-Premises): Python puro, loops otimizados, arquivos locais, banco PostgreSQL (ex-DB2) e MongoDB (ex-IMS).
- Ambiente AWS (Nuvem): AWS Glue Job rodando PySpark, lendo/gravando no Amazon S3, utilizando AWS Aurora PostgreSQL (ex-DB2) e AWS DocumentDB (ex-IMS).

Mapeamento de Paradigmas:
1. IMS Hierárquico ──► NoSQL Documental (JSON Aninhado). Elimina os JOINs pesados, trazendo o segmento inteiro em uma leitura.
2. DB2 Relacional ──► SQL Relacional Moderno. Os loops de FETCH linha por linha do COBOL devem ser convertidos em operações de conjunto em massa do PySpark (DataFrames / .withColumn / .join).
3. Subprogramas ──► Funções isoladas em Python que recebem e alteram dicionários/objetos mutáveis simulando a Linkage Section.
4. Utilitários (ICEGENER / SORT) ──► Traduzidos nativamente para comandos do Spark (`spark.read/write` e `.sort()`), extraindo as chaves lógicas de ordenação de dentro da pasta de `/cartoes_sort/`.

---

### 3. A LÓGICA DO SCRIPT TRANSPILADOR (O MOTOR)
O transpilador foi desenhado seguindo o modelo de compiladores (Grafo de Dependências):
- Passo 1: O motor faz o parse prévio das pastas de suporte (/copybooks/, /dclgen/, /cartoes_sort/, /planos_db2/) mapeando tamanhos PIC X/9, tipos de dados e posições de ordenação em um dicionário global de metadados.
- Passo 2: O motor lê um arquivo JCL específico como o "cérebro" do pipeline. Ele identifica cada `EXEC PGM` e seus respectivos cartões `DD`.
- Passo 3: O motor correlaciona as DDs e os programas customizados com os metadados previamente carregados. Ele gera um único arquivo Python/PySpark estruturado, onde os passos do JCL viram chamadas de funções sequenciais, mantendo o isolamento de escopo e garantindo fidelidade de comportamento e centavos.

---
